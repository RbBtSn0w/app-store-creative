# Managed Lifecycle Contract

## Ownership and Evidence

The runtime lifecycle core owns records and storage. Producers execute capture, composition, and encoding; ASC executes external reads and writes. Keep platform authentication and API contracts in the official plugins.

Use `--help` on each nested command before execution. Record IDs returned by commands; do not infer IDs, success, or ownership from filenames. Source imports are managed artifacts. Attempts require current lease tokens for registration and termination; recover an expired attempt explicitly, preserving the original interruption. Register input dependencies and portable logical paths for all outputs. Standalone producer files are not automatically candidates or approved releases.

## Explicit Archive Choice

Exploration may omit `archivePolicy`. Before producing the run that will be sealed,
choose and declare one shared project policy. The runtime never infers a choice
from installed tools, existing pointer files, or host-local backend configuration.

```json
{"archivePolicy": {"schema_version": 1, "mediaMode": "lfs"}}
```

Allowed modes are `git`, `lfs`, and `external`. An external declaration additionally
requires a portable named `backend`, for example `team-media`; Git and LFS must
not declare a backend. Backend access locations remain in protected host-local
`mediaBackends`, not in the shared policy. The media budget remains in
`artifactPolicy.mediaBudgetBytes`.
This field must be explicitly declared as a nonnegative integer before producing
the run that will be sealed. Omitting it remains valid for exploration, but formal
sealing and independent package verification refuse the undeclared budget. The
budget is advisory: exceeding it produces a warning, not automatic deletion or
a paid-service change.

The original run snapshot binds the declaration. Sealing refuses an undeclared
run even if the current configuration was later changed. Produce a new run after
choosing the policy. Delivery records, manifests, and portable recipes retain the
same choice; independent verification rejects disagreement. Externalization and
publication require the actual retrieved mode and backend to match that choice.
No historical policy is inferred or backfilled.

## Design Approval and Sealing

Validate the candidate, present the exact result to the human, and record a real authorization reference only after approval:

```sh
python3 <runtime-root>/scripts/app_store_creative.py approval record --repo <repo> --candidate-id <candidate-id> --validation-id <validation-id> --actor <human> --authorization-reference <human-message-reference> --confirm APPROVE
python3 <runtime-root>/scripts/app_store_creative.py delivery seal --repo <repo> --candidate-id <candidate-id> --validation-id <validation-id> --approval-id <approval-id>
```

Sealing creates an immutable revision; edits require a new candidate and approval. The returned local delivery path is not itself Git persistence evidence. Use actual full commits and independently verified archive retrieval. Git actions remain separately user-authorized.

Design approval snapshots the run's release target in addition to its candidate, validation, and configuration bindings. Sealing refuses a different target; portable archive verification requires the approved target to match the manifest, with nonempty platform and version. A changed run target makes the approval stale. Missing target bindings are not inferred or backfilled. ASC resource relationships still require independent resolution by the official executor.

## ASC Handoff

The target JSON declares `app_id`, `version_id`, and `platform`. Resolve actual resource identities with the official ASC plugin. A local file or intent never proves an upload.

Target fields must be nonblank strings and the remote platform must match the sealed delivery. The same check applies when creating Git/external plans and when consuming them for upload approval, handoff export, or external preparation. These local checks do not establish that an ASC version belongs to an app or corresponds to the release version; the official executor must resolve those live relationships.

Local and external delivery paths compare revision, project, target, and parent revision with the sealed manifest. External planning checks the independently hydrated package; later consumption reads the manifest from the bound Git commit, verifies its hash, then checks the same delivery identity. Changing the local delivery record cannot relabel an external archive as another project or target. These checks do not repair altered records.

```sh
python3 <runtime-root>/scripts/app_store_creative.py publication plan --repo <repo> --delivery-id <delivery-id> --archive-commit <full-sha> --archive-remote <remote-name> --target <target.json>
python3 <runtime-root>/scripts/app_store_creative.py approval record-upload --repo <repo> --publication-id <publication-id> --actor <human> --authorization-reference <human-message-reference> --confirm APPROVE
python3 <runtime-root>/scripts/app_store_creative.py publication export --repo <repo> --id <publication-id> --confirm
python3 <runtime-root>/scripts/app_store_creative.py publication observe --repo <repo> --id <publication-id> --observation <bound-observation.json> --evidence <executor-evidence-file>
python3 <runtime-root>/scripts/app_store_creative.py publication status --repo <repo> --id <publication-id>
```

The normalized observation must bind plan hash, target, artifact and remote resource identities, gate, source, time, evidence reference, and facts. Do not fabricate observations from upload logs or infer poster readiness from a selected time code. The current runtime consumes normalized evidence; ASC response normalization is not yet a complete automatic adapter. Report that integration gap when it matters.

## Retention and Recovery

Inspect inventory and plan maintenance before mutation. Unknown files remain report-only; candidate/approval/delivery/publication, incident, and lease dependencies protect objects. Quarantine, restore, and purge are distinct operations. Do not delete custom roots, Git history, or remote media caches.

After interrupted relocation, explicitly identify the original workspace for `resume-relocate` or `rollback-relocate`. A switched target needs reverse relocation; interrupted rollback does not undo an activated destination. Independent LFS retrieval is verified against temporary file remotes. Independent external media retrieval is implemented and tested with temporary versioned filesystem backends and exact Git metadata commits. Hosted remote authentication, production backend durability, and the complete real-product source invalidation matrix still require acceptance; temporary backend tests do not prove those gates.


## Record Version Boundary

Lifecycle records must be JSON objects with an integer `schema_version` equal to `1`. Boolean, floating-point, string, missing, and unknown versions are refused when reading. Writers may omit the version and receive the current version; an explicitly supplied unsupported version is refused before creating a record. This version boundary does not replace each entity's required field and provenance validation.

Runs snapshot `workflow` at creation with exactly `name`, `version`, and `implementation`: name `app-store-creative`, integer contract version `1`, and a validated `source-payload-sha256-v1` implementation identity. This snapshot identifies the implementation that started the run; a later runtime does not rewrite it or require its source fingerprint to equal the current runtime. Missing or unsupported workflow snapshots refuse run consumption. There is no compatibility reader or backfill.

Record reads also require the content `id` to match the requested identity. A symbolic link in the record path, including a parent directory alias inside the workspace, is refused. These checks detect mismatched identities and existing aliases; they do not prove protection against every concurrent filesystem replacement race.

Run status uses the same checked reader for attempt start and outcome records. A dangling outcome link is an invalid record location, not evidence that an attempt is still running.

Archive verification requires an object manifest with integer version `1` and list-valued `files`, `assets`, and `recipe_inputs`. File sizes are nonnegative integers and hashes are lowercase SHA-256 values. Media and recipe input bindings must match both the path and hash of the file manifest; an existing path alone is insufficient.

Media bindings belong under `media/` and recipe inputs under `recipe/inputs/`. Bindings must completely cover the files in their namespace, with unique artifact identities; distinct source identities may share one path only when bound to the same file hash. Only `screenshot`, `preview`, and `poster` are deliverable media roles; evidence is not uploadable media.

Rendered evidence is sealed under `evidence/render/`. The derived input alias index is checked against all registered imported source paths and hashes; it is recipe metadata, not a source artifact.

Portable verification cross-checks candidate, passing `media-v1` validation, and design approval evidence, including candidate hash, selected asset order, run/validation identities, configuration hash, and nonempty human authorization reference. This establishes internal consistency; a reference string alone does not authenticate human consent. Keep the trusted manifest hash and authorization provenance supplied by the owning workflow.

Sealed archives contain `evidence/provenance.json`, preserving the selected roots and their complete dependency closure with producer terminal states. Verification rejects cycles, missing or unrelated nodes, failed or partial outputs, and file/binding mismatches. Lease tokens are not exported. The graph proves internal provenance consistency, not the authenticity of a real product capture or human consent.

Design and upload approval creation share one authorization metadata validator. Both actor and authorization reference must be nonblank strings; invalid values are refused before writing an approval. This input check does not authenticate the human source of the referenced authorization.

Approval consumption rechecks authorization metadata and scope. Publication status, handoff, and sanitized approval export share the same upload predicate, including exact target and plan hash. Invalid approval metadata remains pending. Sealing rechecks design authorization and configuration binding before producing a package.

Run history and sealing share the same design approval check. Invalid authorization metadata or candidate/validation/configuration bindings produce `STALE` with reasons in status, and sealing refuses them.

Local approval and sealing require a `media-v1` validation bound to the candidate's run, with `PASS` and an explicit empty error list. Unknown policies or inconsistent PASS records cannot authorize delivery.

Retention protects dependencies through the same iterative closure traversal as production and archive verification. A cycle or missing node in the protected reference graph refuses the cleanup plan; object integrity and quarantine checks remain maintenance-specific.

Use `delivery --repo <repo> status --id <delivery-id>` to recheck sealed package, recipe, provenance, and delivery identity bindings without writing records. It reports local PASS/FAIL with reasons; remote status remains UNKNOWN. Local archive integrity does not prove upload completion.

Studio exposes `GET /api/deliveries/<delivery-id>` using the same delivery status verifier. A known corrupt package returns a local FAIL result with reasons; an unknown identity returns 404. The endpoint does not write records or imply remote completion.

Find historical deliveries with `delivery --repo <repo> list --limit 20 [--cursor <id>]` or `GET /api/deliveries?limit=20&cursor=<id>`. Records are sorted by creation time and identity; new deliveries do not shift an existing cursor. Summary metadata is not current verification evidence: use delivery status for each package.

## Reverse Relocation

A switched destination returns through `storage plan-reverse-relocate`, `verify-reverse-relocate`, `prepare-reverse-relocate`, and `switch-reverse-relocate`. Preserve the workspace path active before the reverse operation. Use `resume-reverse-relocate --source-workspace <that-path>` after interruption; the configured workspace may already point elsewhere. Preparation does not switch roots. Review and apply actual staging ignore rules before copying.

Reverse execution persists intent, fences source writes, exchanges occupied original roots or publishes missing roots, checks bytes, updates configuration and binding evidence, syncs directories, and activates the target. Original copies remain at `preserved_backups`; no deletion is implied. Sync failure after an exchange must resume by recorded directory identities, never blindly exchange again. Completed recovery rechecks receipts without modifying current data. Verified activated forward or reverse operations can be reversed again. Repeated roots use journaled location projections: pin exact predecessor bytes and prior switch receipts, retain immutable history, then publish the new view. Interrupted rollback restores prior views and only removes a newly introduced view whose exact bytes and journal match. Temporary-workspace tests cover full-root and shared-workspace cycles, resume, rollback and evidence tampering; backup retention, complete filesystem races, process-interruption validation and real-product end-to-end acceptance remain incomplete.

Interrupted reverse switches may use `rollback-reverse-relocate --source-workspace <workspace-before-reverse> --confirm ROLLBACK`, with actor and reason. It verifies source data, backup bytes, directory identities and configuration, persists rollback intent, restores root positions and source configuration, retires owned pending controls without losing evidence, then releases the source fence after sync. New staging remains preserved. Once rollback starts, continue rollback; forward resume is refused. An activated target refuses interrupted rollback. Do not use forward relocation recovery commands for reverse plans.


## Relocation Backup Inventory

`inventory` and Studio `GET /api/inventory` share the same core read. `relocation_backups` verifies activated forward source copies and reverse backups against plan, preparation, intent, receipt, recorded directory identity and full file hashes. Forward plans pin source-root identities; the pre-switch source-tree manifest hash is bound to the receipt and rechecked by recovery. Only exact, authority-matching controls added by that switch are exempt from extra-file reporting; unknown files remain visible. It reports VERIFIED, CHANGED, MISSING, IDENTITY_CONFLICT, UNSAFE or ACTIVE_CONFLICT; invalid operation evidence and directory-read failures remain unverified. Unknown files are preserved. Unobserved bytes remain null, and capacity exposes unobserved-copy and unverified-operation counts. This is not cleanup approval. Operation-bound staging and pending roots are reported separately with phase and content status. PREPARED receipts pin canonical creation-proof hashes in staging_root_proof_sha256. Preparation, switch, forward resume, reverse recovery/rollback and inventory verify those bindings before using directory identities; missing identity evidence or a changed ownership marker stays UNVERIFIED_OWNERSHIP. Partial contents, unknown files, published pending targets and reverse pending backups remain visible. Backup retention and reclamation remain incomplete. The HTTP endpoint accepts no arbitrary path query.


Relocation-copy retention planning uses `cleanup plan-relocation-retention --retention-days <days>` with an explicit nonnegative policy. Only registered CAS objects at their recorded physical positions in verified completed copies may be eligible. Each candidate pins a verified independent active object, hash, size and file identity. Work files, metadata and recovery controls remain protected. Pending or unverified operations, configured source paths, unexpired retention, corrupt or missing recovery media and same-inode hardlinks prevent eligibility. This is a durable plan, not execution authorization; copy preparation, quarantine commit, restore and purge use the dedicated commands below and revalidate at execution time. Existing object cleanup commands do not accept these plans.


`cleanup verify-relocation-retention --id <plan-id>` revalidates the same retention state under the lifecycle transaction. Plans bind retained-file identities, independent recovery identities, live configuration and all non-maintenance lifecycle record contents. Same-byte file replacement, new runs, changed references or recovery media make the old plan stale. Additional maintenance plans do not invalidate the reference snapshot. Verification returns READY and eligible counts without creating a new record or modifying media. It accepts only relocation retention plans. A later execution must run this gate within its transaction and provide interruption recovery; an earlier READY result is not authorization for later filesystem mutation.


Relocation quarantine preparation uses `cleanup prepare-relocation-quarantine --id <retention-plan-id>` and `cleanup resume-relocation-quarantine-preparation --id <operation-id>`, each requiring actor, reason and `--confirm PREPARE`. Preparation revalidates the plan, persists operation/directory identity and per-file creation evidence, exclusively creates payloads relative to a verified directory FD and copies eligible objects, verifies hashes and identities, syncs files and ancestors, then revalidates references before writing PREPARED. The prepared receipt binds operation hash and copy identities with source_removal_executed=false. Source removal is not implemented by these commands. Complete payloads can resume after sync interruption; partial or corrupt payloads, replacement identities, aliases and unknown files are preserved and refused. First preparation-failure evidence is immutable. Managed preparation media lives under workspaceRoot/maintenance/relocation-quarantine; inventory, removal commit, restore and purge are provided by the dedicated use cases below; preparation alone does not execute them.


Shared inventory adds quarantine_preparations for CLI and Studio /api/inventory. Preparation phase and observed content status are independent. Operation/plan hashes, configuration authority, derived paths, directory identity, creation records and prepared receipt bindings are checked before scanning. Replacement files, changed bytes, extra files and links are reported; unsafe or missing roots remain unobserved, and unreadable trees or invalid evidence remain unverified. Capacity exposes observed logical bytes, inode-deduplicated local block estimates and unobserved/unverified counts. This is read-only preparation inventory, not source-removal approval. The read-only inventory UI, removal commit, restore and purge are implemented as separate use cases; full maintenance action views and real-product acceptance remain incomplete.


Relocation quarantine commit and restore use dedicated cleanup commands with QUARANTINE/RESTORE confirmation, actor and reason. Commit validates the preparation and retention snapshot, syncs a commit intent, then exclusively displaces each original file within its parent using a verified directory FD. Original inode and complete bytes remain in the reserved source-side location; independently prepared media also remains. This removes the original path, not media bytes. Interrupted commit revalidates logical pre-displacement state using only intent-bound exact identities and hashes; new references prevent further moves. Restore preflights all locations, validates bound receipts and identities, never overwrites a conflicting original path and can resume after receipt interruption. It permits new references because it restores bytes. Inventory exposes COMMIT_STARTED, QUARANTINED, RESTORING and RESTORED, with unknown removal completion for partial execution. Retained-root inventory recognizes verified source dispositions as QUARANTINED, listing operation-bound relative and retained paths, hashes and sizes without changing original manifests. Unknown files, corrupt bytes and invalid evidence remain visible; disposition_errors prevent new cleanup selection. Restored roots return to VERIFIED; reverse relocation requires restoration first. Purge and maintenance/relocation coordination use the dedicated gates below; full retained-source projections, broader races and process-interruption verification remain incomplete.


Relocation quarantine purge planning uses `cleanup plan-relocation-purge --id <quarantine-operation-id>` (default quarantine retention seven days) and `cleanup verify-relocation-purge --id <purge-plan-id>`. Plans list only source-side retained media and prepared copies, pin file/parent identities, hashes and sizes, and bind independently verified current registered objects. Restore or purge intent, pending/unverified relocation evidence, configured source paths, incident dependencies, non-independent or corrupt recovery objects and abnormal retained roots refuse planning. Revalidation binds live configuration, all non-maintenance lifecycle records, inventory and immutable operation receipts. Changed references, identities or edited paths make plans stale. This is a distinct relocation-purge-plan; ordinary trial-object purge must not execute it. Actual deletion uses the dedicated executor below; no bytes are removed by planning or verification.


`cleanup purge-relocation --id <relocation-purge-plan-id>` requires actor, reason and `--confirm PURGE`. It revalidates the plan, syncs purge intent, then records each file checkpoint before exclusively capturing the exact inode relative to a verified parent FD and deleting the captured file. Every step rechecks immutable plan/intent, references, independent recovery and complete protected-root file sets. Only checkpoint-bound missing media is accepted on original-plan retry. Other plans cannot take over, restore stops at purge intent, and reappearing files are preserved. Completion retries verify receipts, checkpoints and remaining guard files. Inventory exposes PURGING/PURGED and source purged_files with PURGED/PARTIALLY_PURGED without changing original manifests. Logical bytes removed do not establish physical space savings. Metadata, unknown files and active objects are retained. Maintenance/relocation coordination is implemented through the gates below; full historical retained-source projections, broader races, explicit reconstruction after purge and real process-interruption acceptance remain incomplete.

## Maintenance and relocation coordination

Forward and reverse relocation planning, revalidation, and preparation reject unfinished maintenance. An uncommitted relocation quarantine preparation can be cancelled with `cleanup cancel-relocation-quarantine-preparation --id <operation-id> --actor <owner> --reason <reason> --confirm CANCEL`. Cancellation records an immutable terminal receipt and preserves every file; it forbids further preparation or commit and does not reclaim space. Commit or purge intent prevents cancellation. Verified cancellation, restoration, or purge terminal metadata permits new relocation plans, including historical bindings resolved through verified switches. Completed relocations bind quarantine directory and file identities in the prepared receipt. Inventory resolves current copies through verified activation and switch evidence, including reverse returns to the same paths, without rewriting maintenance records. Cancelled/restored copies retain their terminal phase and report actual content; relocated purged copies retain checkpoint-bound removal evidence and observe current empty roots. Interrupted forward resume and reverse resume/rollback revalidate quarantine identities at journal-resolved locations before further mutations. Reverse switch receipts also bind quarantine trees in preserved destinations; recovery checks both copied data and preserved backups. Full retained-source projections, parent-path races, and real process-interruption acceptance remain incomplete; these observations do not authorize cleanup.

## Observation completeness

A confirmed absent directory is distinct from an unreadable tree. Directory-walk or file-lstat failure sets that area's counts and sizes to null and adds a scoped observation_errors entry with area, path and reason. Unreadable objects expose registered identities in unobserved_registered rather than reporting them missing. Empty quarantine/purge arrays in an unobserved object tree do not prove zero presence. Other readable areas remain observable. An unreadable or unsafe authoritative record tree fails the inventory request instead of returning partial references. Retention planning and execution require complete records and object observation; relocation snapshots require complete relevant storage observations and strict file enumeration. An earlier inventory response does not bypass execution-time checks. Injected read-failure acceptance does not establish real OS-permission, parent-path race or process-interruption safety.

## Configuration layers and authority

The read-only configuration_layers module composes built-in defaults, shared project storage, then host-local per-root overrides. The selected creative.config.json maps to adjacent creative.config.local.json; custom names derive the same .local suffix. A local document requires schema_version=1, matching project_id and storage; optional mediaBackends holds named filesystem access locations. It cannot override recipes, approvals or publishing. Git worktrees require real ignored and untracked evidence, including negated rules; reading does not modify rules or the index. Both document hashes and local absence bind the revision, with regular-file identity checks, duplicate-key refusal and re-observation before return. Callers must still revalidate before mutations. This resolver binds relocation planning, configuration write evidence and the internal Lifecycle.from_configuration runtime factory. Managed CLI and Studio readers, shared conditional saves, capture import, poster extraction and screenshot production use protected host-local overrides. Forward owning-layer relocation supports local targets; reverse local relocation is integrated; exhaustive acceptance remains incomplete. There is no standalone compatibility integration requirement. Runtime adoption must preserve portable recipe identity, strip local paths from archival/exported evidence and update the appropriate layer during relocation.


The layer foundation also provides read-only plan_storage_change and verify_storage_change. A change pins both source document bytes/hashes, file identities/modes and local absence, plus recipe identity and exact target bytes/path/revision. With no local file it targets the shared storage section; with a local file it targets only that file and materializes a complete root set so omitted values cannot fall back to old shared locations. Verification reloads the caller-supplied project authority, rechecks actual Git protection and regenerates the whole plan; edited paths/payloads, changes to either document, same-byte inode replacement, permission changes and local creation/deletion invalidate it. Source bytes are private operational recovery evidence and must not enter exported recipes or publication records. These functions do not write, authorize a save or implement relocation/recovery. Production adoption must journal the owning-layer update and bind both source/target document states before activating the new storage.


Existing forward relocation plans now bind configuration_change evidence from the layer foundation when a shared authority file exists. Revalidation, preparation and pre-fence switching regenerate this evidence, including host-local absence and shared file identity. Newly appearing local configuration, same-byte source replacement, or edited target proposals make the plan unusable before staging/intent writes. A plan without a shared file explicitly records no change authority and becomes stale if that file appears; switching still requires a regular authority file. A local-only configuration without shared recipe authority is refused. Forward local-layer switching and interrupted recovery use the owning document contract; reverse local relocation is integrated; exhaustive acceptance remains incomplete.


Reverse planning and pre-exchange verification also bind configuration_change for the current active source and exact original-root target. Same-byte source identity replacement, local appearance and edited layer proposals refuse preparation or exchange. Shared-owner forward resume/rollback and reverse intent validation recheck host-local absence before further writes, swaps or configuration overwrite. Newly introduced local files remain preserved and block recovery; recovery does not delete them. After explicitly restoring the reviewed layer state, the original operation can continue. Shared configuration is still validated against journal-allowed source/target bytes across atomic commits; its original inode is not incorrectly required after an intentional configuration replacement. Reverse local-layer switching is integrated; true process-interruption safety and all parent-path races remain incomplete.

The internal configuration_preparation module stages a verified owning-layer update beside its target using exclusive creation and private permissions. Its workspace journal binds the complete plan, actor, reason, parent identity and staged file identity. Actual Git rules must protect both payload and journal before writes. PREPARED means the payload was synchronized and revalidated; storage_activated remains false and both source documents remain unchanged. Complete payloads can resume preparation after sync interruption; partial, substituted, stale or unowned files are preserved and refused. This foundation has no public command and does not yet commit configurations, activate storage, retire staging or enable host-local runtime overrides.

Prepared configuration returns use verify_prepared_storage_change to reobserve the complete plan, intent, creation proof and prepared receipt. The verifier checks owning target bytes, file and parent identities, source layers, storage binding and actual Git protection, and performs no writes. Every private journal path is checked before any preparation write, including an absent file that is still force-tracked in the Git index. A complete payload without its prepared receipt is not committed evidence. Switch executors must use this verifier before replacement; forward and reverse switching and resume are integrated; forward and reverse rollback share the restoration identity contract.

Forward relocation switching now prepares and verifies its owning configuration payload under the existing source lock. Its preparation records are stored as configuration-* suffixes within the relocation journal, excluded from the media snapshot and transferred with the operation evidence. After publishing target roots, switching revalidates the source layers and staged payload before copying those exact bytes into the mode-preserving atomic replacement file. Source identity substitution or staged payload modification leaves the operation interrupted and the source configuration intact. Relocation Git policy includes exact private configuration staging and journal suggestions. Reverse switching and interrupted switch resume share these proofs; host-local target switching remains refused.

Forward resume now verifies the exact switch-intent preparation reference and, while source configuration bytes remain installed, revalidates both source layers and staged evidence before any recovery mutation and again before replacement. Same-byte source or staged identity substitution is refused without creating resume intent. Recovery after target replacement now uses the pre-rename installation proof described below; reverse switching and resume share the installation proof; forward rollback uses the restoration proof described below.

Forward configuration installation records the replacement inode before rename, including device, inode, mode, size and mtime, bound to the plan and preparation hashes. ctime is excluded because rename changes it; target bytes remain independently verified. Both pre-rename and post-rename recovery require this proof, preserving substituted or unowned files and refusing same-byte replacement inodes. Existing proofs are revalidated and their directories resynchronized before retrying replacement. Late installation evidence is transferred to target operation records. Exact Git suggestions cover installation staging and proof. Unjournaled orphan temporary files are preserved and refused; their retirement, complete parent/rename race protection and real process-interruption validation remain pending.

Forward rollback revalidates original source-layer identity or the installed target inode before creating rollback intent. Restoration uses the same journaled replacement contract, bound additionally to rollback intent and exact original bytes. Interrupted restoration can continue only at its own recorded restored inode; same-byte external replacements at source, installed or restored paths and substituted restoration temporary files are preserved and refused. Configuration identity is rechecked after media validation before completion. Git suggestions include restoration staging and proof. Host-local writes, staging retirement, full path races and real process-interruption validation remain pending.

Reverse switching prepares its configuration under the existing source lock and binds the exact preparation receipt in switch intent. Execution and resume verify source-layer and staged identity before exchanges and again before replacement; after replacement they require the recorded installation inode. Late installation proof is transferred to the returned workspace. Reverse Git suggestions cover configuration staging and journals. Retained forward source inventory treats installation proof as an owned late control only after checking its plan and preparation bindings; unknown files remain extra files. Host-local target writes and staging retirement remain pending.

Reverse rollback now checks original source-layer, installed or restored inode evidence before mutations and again before directory reverts and configuration replacement. Its rollback intent binds source_config_sha256 as well as switch_intent_sha256. Restoration uses the shared pre-rename inode journal, bound to that immutable intent and exact original bytes. A sync interruption after restoration can continue only at the recorded restored inode; same-byte external replacements and source changes during root reverts preserve files and refuse completion. Actual Git protections cover restoration staging and proof. Shared-workspace control retirement and preserved backup verification remain part of the existing rollback path. Host-local owning-layer relocation, orphan/staging retirement, full path races and process-interruption acceptance remain incomplete.
